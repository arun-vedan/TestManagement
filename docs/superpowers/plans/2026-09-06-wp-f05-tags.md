# WP-F05 — Tags

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** let a tester label any entity with free-form tags and then find everything carrying a tag.

**Architecture:** a first-class `tags: [String]` array on all five entity models, one shared tag editor in the detail kit, a tag column in the list, and click-a-tag-to-filter using the server-side query path that already exists.

**Spec:** `docs/superpowers/plans/2026-09-05-functional-gaps-program.md` — work package F05, the first of Wave F2.

---

## What was verified before this plan was written

Three of the last four packages were planned on a register premise that turned out false. These were each checked against source or live data.

- **No tag or label field exists on any model.** `grep` across every `backend/*/models/*.js` returns nothing. The register's premise holds.
- **Server-side filtering already works, and tags get it for free.** `shared/service-core/middleware/advancedResults.js:48-58` copies `req.query` (minus `select`/`sort`/`page`/`limit`) straight into the Mongo filter. Mongo matches a scalar against an array natively, so `GET /api/v1/testrepo?tags=regression` returns every test case whose `tags` array contains `regression`. **No backend query code is needed** — only the field.
- **The grid's own column filter is off and is not the mechanism.** `EntityList.tsx:142` sets `disableColumnFilter`, and `api/entityGridApi.ts:31-34` says so explicitly: filtering here means a saved view's `queryParams`, not the DataGrid's filter UI.
- **The filter path is half-wired, and this is the important one.** `EntityList.tsx:51` *applies* `selectedView.queryParams` through `resolveViewQueryParams`. But line 116 hands `getCurrentViewState` a hardcoded `queryParams: {}`, so **saving a view always stores an empty filter.** The machinery can apply a filter it can never capture. A `tags` field without an affordance would therefore be decoration — which is why Task 3 exists.
- **Custom fields were considered and rejected as the mechanism.** `fieldsService` has a `fieldType` enum and `FieldGrid` renders per type, so a `'Tags'` type was a real option. Rejected because its values would land in `dynamicFields.<adminChosenName>` — and verified today: **nothing in the codebase filters on `dynamicFields`, and it is not indexed anywhere.** Building tag filtering on that would be unproven ground under a name that varies per project. Owner decision, 2026-09-06: first-class field, all five modules.

## Tag vocabulary — decide once, here

- **Free-form**, not a managed list. No admin screen, no tag CRUD. A tag exists because something carries it.
- **Stored lowercase, trimmed**, so `Regression`, `regression` and ` regression ` are one tag. Normalise on write, in the model, so every path gets it.
- **No spaces** — a tag is one token. Reject rather than silently rewrite, so the user learns the rule.
- **Deduplicated** per entity.
- Suggestions come from what already exists in the project (Task 2), not from a curated vocabulary.

- [ ] **Step 3: Add the field to all five models**

Add to each schema, at the top level, beside the other simple fields:

```javascript
    // WP-F05 -- free-form tags. Additive and defaulted, so every existing
    // document reads back unchanged with an empty array; no migration was
    // needed or written.
    //
    // Indexed because the whole point is filtering: advancedResults copies
    // ?tags=<value> straight into the Mongo filter, and a scalar matches
    // any element of an array natively, so the query path needed no code
    // at all -- only this field and this index.
    //
    // Normalised in a setter rather than in each controller so EVERY write
    // path gets it: create, update, bulk, CSV import and anything added
    // later. Lowercased and trimmed so 'Regression', 'regression' and
    // ' regression ' are one tag; de-duplicated; a tag containing
    // whitespace is rejected by the validator below rather than silently
    // rewritten, so the rule is learnable.
    tags: {
      type: [String],
      default: [],
      index: true,
      set: (values) => {
        if (!Array.isArray(values)) return values;
        const cleaned = values
          .filter((v) => typeof v === 'string')
          .map((v) => v.trim().toLowerCase())
          .filter((v) => v.length > 0);
        return [...new Set(cleaned)];
      },
      validate: {
        validator: (values) => Array.isArray(values) && values.every((v) => !/\s/.test(v)),
        message: 'A tag cannot contain whitespace -- use one token per tag (e.g. "smoke-test", not "smoke test")'
      }
    },
```

**The setter runs before the validator** — **verified 2026-09-06**, so this is settled and does not need re-checking: every create and update path in these four services goes through `create()` or `findOneAndUpdate()` with `runValidators: true`, and both apply setters before validators. A value of `'not one token'` is therefore trimmed and lowercased, still contains a space, and fails validation with a 400.

Check each schema's existing style and match it — some use the terse `{ type: String }` form and some the expanded one.
