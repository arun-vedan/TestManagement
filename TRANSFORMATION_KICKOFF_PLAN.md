# srckubetest — Transformation Kickoff Plan

**Purpose**: This is the executable companion to [`ENTERPRISE_TRANSFORMATION_STRATEGY.md`](ENTERPRISE_TRANSFORMATION_STRATEGY.md). That document analyzed the repository and defined an 8-phase enterprise roadmap (Section 47), two prioritized backlogs (Sections 45–46), a technical debt register (Section 44), and a risk register (Section 49). This plan breaks that roadmap into concrete, sequenced, sprint-sized work with acceptance criteria for each task — **Phase 0 (Stabilization) and Phase 1 (Technical Foundation) are complete** (see their sections below for the full record of what was done); **Phase 2 (Core Governance)** is planned in the same detail, informed by real velocity/risk data from Phases 0–1 rather than designed in the abstract, per the Sprint 1.2–1.3 retrospective's recommendation. Later phases (Enterprise Governance & Security onward) remain at the roadmap's existing level of detail and referenced, not re-derived, since they depend on decisions only Phase 2 work will surface.

**Assumptions made to sequence this plan** (flag/adjust if wrong): a small team (consistent with the single-author-dominated commit history observed in Phase 1 of the strategy doc) working in 2-week sprints; no committed production traffic yet (Section 37 of the strategy doc flagged this as unconfirmed — **verify this before Sprint 0.1**, since it changes whether Task 0.1 can run without a maintenance-window coordination step).

---

## How to use this plan

- Each task cites the exact backlog ID (`TB-xx`/`PB-xx`) and technical-debt ID (`TD-xx`) from the strategy doc, and the exact files involved — no re-analysis needed, just execution.
- **Do not start a sprint's tasks out of order within a phase** unless a task explicitly says it can run in parallel — several early tasks (secret rotation, route auth fixes) are prerequisites for tasks later in the same phase.
- **Do not begin Phase 1 tasks before every Phase 0 exit criterion is met.** Phase 0 closes actively exploitable issues; starting refactoring work on top of an insecure baseline just means refactoring insecure code.

## Sprint 1.2–1.3 retrospective (Task 1.3.4)

**What went right**: the shared-library pattern from Sprint 1.1 held up under a real test — building a brand-new service on it from scratch was fast and mechanical (models/controllers/routes ported with almost no changes beyond import paths). The strangler-fig sequence (stand up → cut Kong over → leave old ones running → decommission last) worked exactly as designed: at every point there was a one-line Kong revert available, and it was never needed. Writing black-box HTTP tests against the real running container (rather than fighting `server.js` into an in-process-testable shape) turned out to be the right call for a codebase with zero prior test infrastructure — it tests what's actually deployed, not a refactored stand-in.

**What went sideways**: two planning documents (this one and the strategy doc) had confidently stated a specific technical claim — "consolidating testPlan+testExecution removes the one proven inter-service call" — that was simply wrong, and it went unnoticed until it was about to become the premise for actual consolidation work. The frontend dead-code assessment (TD-12) had the same shape of problem at smaller scale: "AuthProvider is dead" was half-right (the Provider itself is dead) and half-wrong (a widely-used hook depended on it in a way that wasn't dead, just inert) — deleting first and checking later would have broken 10+ live pages.

**The pattern underneath both**: earlier analysis (however thorough) is a hypothesis, not a fact, the moment you're about to act on it. Both mistakes were caught by re-verifying against the actual code/running system immediately before acting, not by the original analysis being extra careful. Worth carrying forward explicitly into Phase 2 and beyond: treat every "per the strategy doc" reference as something to spot-check against current reality before it drives an irreversible step, especially for claims about *what depends on what*.

**Go/no-go on consolidating the remaining 8 services**: **go, one at a time, same strangler-fig sequence** — verify the actual coupling/dependencies of each target pair fresh (don't trust the strategy doc's target-architecture groupings without a quick re-check first, per the lesson above), stand up, cut over, write the black-box test suite, hold decommission for one real user-driven check. No change to the overall sequencing already laid out in Phase 4 §34 of the strategy doc, only to the specific factual claims within it (now corrected).
